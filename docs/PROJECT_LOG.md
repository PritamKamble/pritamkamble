# Project log

Living record of decisions, architecture, and open items for the Pritam Mentor platform. Git history is the source of truth for *what* changed and *when* — this doc exists for the *why*, and for what's still open, since that context doesn't survive in commit messages alone. Update this when a session makes a real decision or ships something structural, not for every small fix.

## What this product is

A 1-on-1 mentorship platform (Full-Stack + GenAI) with three sides:
- **Candidates** — invite-only, track daily work logs, apply to jobs, self-report progress
- **HR/employers** — self-serve signup, post jobs, browse candidates
- **Admin** (the mentor) — manages the waitlist funnel, invites candidates, schedules interviews, reviews daily logs

Stack: Next.js (App Router) + Supabase (Postgres, Auth, Storage, Edge Functions), deployed on Vercel. No paid tier assumptions — kept intentionally lean for early-stage volume.

## Current architecture at a glance

- **Auth**: fully passwordless. Every role logs in via magic-link email, with a 6-digit OTP code as a fallback for when the link fails to click through cleanly (common on mobile, cross-app). Candidates are invite-only — no self-serve candidate signup exists anywhere; HR keeps self-serve signup since there's no queue/scarcity story to protect there.
- **Single auth callback** (`/auth/callback`) handles session establishment for every flow (login, invite, HR signup), and handles both auth flow types Supabase can hand back (`?code=` PKCE and `#access_token=` implicit) since admin-generated links (invites) use implicit while browser-initiated ones use PKCE.
- **RLS everywhere** — all 7 tables have row-level security, verified by direct attack-testing (not just reading policy text) at least once this session.
- **IaC hygiene**: `supabase/migrations/`, `supabase/functions/`, and `supabase/templates/` in git are the reviewable source of truth. Migrations and edge functions actually deploy via the MCP tool; email templates are dashboard-only (no push tool available) so those still need a manual paste when changed — documented in `supabase/templates/README.md`.
- **Daily-nudge & status-change emails**: two Edge Functions (`daily-nudge`, `application-status-notify`) triggered by `pg_cron` and a DB trigger respectively, both authenticated via a shared secret stored in Supabase Vault (not in git, not hardcoded in any migration).
- **AI blog pipeline**: `generate-blog-digest` runs daily via `pg_cron`, pulls hiring/tech-trend items from free sources (Hacker News API, GitHub release feeds for curriculum-relevant repos, RemoteOK), drafts a post with Claude grounded strictly in those sources, and inserts it into `blog_posts` as `status='pending'`. Nothing goes live automatically — admin has a new "Blog" tab to review/approve/reject, and only `status='approved'` posts are readable by the public `/blog` and `/blog/[slug]` pages (enforced by RLS, not just UI). Requires an `ANTHROPIC_API_KEY` Edge Function secret that is **not yet set** — the function returns a clear 500 until it is.

## Key decisions and why

- **Candidates invite-only, HR self-serve** (2026-08-06) — the whole landing page sells "small batch, personal mentorship, apply to a queue," but self-serve candidate signup let anyone bypass that entirely. Closed by removing the signup path and gating creation behind an admin-only "Invite a candidate" action.
- **Passwordless over password+reset** (2026-08-06/07) — password-reset redirect bugs kept recurring (wrong domain, missing allow-list entries, wrong template variables) across several rounds of debugging. Removing passwords entirely removed the whole flow class, not just patched the symptom.
- **OTP code as a fallback, not a replacement, for the magic link** (2026-08-07) — the recurring "PKCE code verifier not found" failure is structural to link-based auth (opening the email in a different browser/app context than the one that requested it). A typed code has no code_verifier dependency, so it sidesteps the failure class entirely rather than just improving the error message.
- **Self-reported progress fields explicitly labeled** (2026-08-06) — `weeks_completed`/`dsa_solved` are candidate self-entry with no verification step, but were being shown to employers without that caveat (and the marketing copy on the employer page briefly overclaimed "not self-reported" — since corrected).
- **No monetization model decided yet for the employer side** — currently "free, always." Deliberately undecided, not an oversight — flagged as open in an earlier review.
- **Candidate project links added** (2026-08-07) — the employer page promised candidates' work is verifiable via "live project links," but no such field existed anywhere; only a resume upload. Added `candidate_profiles.project_links` (jsonb array) so the marketing claim matches what the product actually does.
- **Interview feedback surfaced to candidates** (2026-08-07) — admin-entered evaluation notes on completed interviews were previously admin-only; the candidate only ever saw a bare score. Added an "Interview feedback" card on the candidate's My Progress tab showing the full notes, not just the number — the notes were the part that made the review valuable.
- **Video calling as a plain meeting-link field, not built-in calling** (2026-08-07) — offered candidate a choice between a meeting-link field, embedded Jitsi rooms, or full custom video infra; chose the meeting-link field as the lowest-effort option that still solves the actual problem (admin already uses Zoom/Meet day to day). Admin pastes a link when scheduling (`interviews.meeting_link`); candidate sees a "Join call" button on the upcoming-interview card, admin sees a "Join →" link in the Interviews tab.
- **AI blog: curated free sources, not an open crawl; admin approval is a hard gate, not just UI** (2026-08-07) — asked to "crawl the internet daily" for blog content; pushed back on a true open crawl since no source control means no quality control on content published under the mentor's name. Started with a specific set of free sources (HN, curriculum-relevant GitHub release feeds, RemoteOK) instead of a paid search API. Approval is enforced by RLS (`blog_posts` public-read policy only matches `status='approved'`), not just an admin UI convention, so a bug in the admin page can't accidentally leak an unapproved post to `/blog`.
- **Employer lead-gen form on `employers.html`, no account required** (2026-08-07) — the only way to post a role was full HR signup, which is real friction for a first-touch employer just testing interest. Added a public "Tell us what you're hiring for" form that leads with the opening(s) (title/type/track, repeatable via "+ Add another opening") and asks for contact info only after, with company name explicitly optional — matches the ask to highlight the opening over company details. Submissions land in a new `employer_leads` table (`status`: new/contacted/converted/closed) reviewable in a new "Opening leads" panel at the top of the admin Employers tab, with a status dropdown per lead. No email notification wired up yet — admin has to check the tab.
- **Found and fixed a real RLS bug while testing the above** — first live test of the new `employer_leads` insert failed with an RLS violation even though the policy looked right. Cause: the policy was scoped `to anon` only, so a visitor who happened to still have an authenticated session open in another tab (HR/candidate/admin login on the same device) would get their submission silently rejected instead of the insert going through. Fixed before ever shipping it (not scoped to a role at all now). Went back and found the exact same pattern on the original candidate-waitlist form (`applicants` table, `"anon can apply"` policy, live since 2026-08-06) and fixed that too (`20260807140000_fix_applicants_insert_policy.sql`) — that one *had* already shipped and could have been silently rejecting legitimate waitlist submissions this whole time.
- **Admin login flow audit: no discoverable entry point, and an unnecessary extra redirect hop** (2026-08-07) — asked as a UX/BDE check "does admin have to type the URL manually, and where does he land after login." Traced it: functionally correct (always ends up on `/admin`), but two real gaps. (1) Zero links to `/login` anywhere on the public site — had to know/bookmark the URL, with no recovery path if forgotten and nothing to hand a future co-admin. Added a quiet "Mentor Login" link (→ `admin.pritamkamble.com`) next to the existing "Employer Login" in the `index.html`/`employers.html` footers — deliberately not on `freshers.html`, which already funnels to the main site. (2) Every login (not just admin's) was bouncing through an intermediate `/portal` page that did nothing but look up `profiles.role` and redirect again - a full extra page load on every single sign-in. Moved that role lookup inline into `/auth/callback` and the OTP-verify handler in `login/page.tsx`, so a plain login now goes straight from "verify code" to `/admin` (or `/candidate`/`/hr`) with no visible `/portal` hit at all. `/portal` itself is untouched as a fallback for the no-session/no-profile edge cases. Verified live: real OTP login, confirmed zero network requests to `/portal`.

Found the live **Invite user** template on the Supabase dashboard was a completely different, unbranded plain-text version with no OTP code fallback at all — worse than the magic-link/recovery gap found earlier the same day. Fixed by replacing it with the branded `invite.html` content directly in the dashboard. Also found the three auth templates had three different live subject lines (`config.toml` says "sign-in code" for all; dashboard had "sign-in link" and a bare "Sign in to Pritam Mentor") — normalized to match `config.toml`. `application-status-notify` was literally interpolating the raw `status` enum value (e.g. "was updated to: **rejected**") into the candidate-facing email body — replaced with real per-status copy. Finally, brought the 3 plain edge-function emails up to the same visual bar as the auth templates: added a shared `emailShell`/`emailButton` helper (duplicated per-function rather than a shared import, matching this codebase's existing self-contained-function style) giving each the same dark header/white card/branded button, plus hidden preheader text and a `text` plain-text fallback alongside `html` on every Resend call. Verified live: triggered a real digest email with an overdue follow-up, confirmed the new branded rendering in Gmail.
- **Live email templates found drifted from the repo** (2026-08-07) — the Magic Link and Recovery templates in the Supabase dashboard were missing the entire "enter this code instead" block (only the sign-in link was there), despite `supabase/templates/README.md` claiming they matched as of this same date. Real-world effect: users saw the login page promise a 6-digit code, but the actual email had no code, so the OTP fallback (added earlier this session specifically to work around magic-link failures) was silently broken in production. Fixed by hand-editing both templates directly in the dashboard and verifying with a real inbox. Since there's still no push tool, this class of drift (repo says X, dashboard has Y) can recur silently — worth spot-checking the live templates occasionally rather than trusting the repo copy.
- **Table status `<select>`s and mobile applicants table fixed** (2026-08-07) — status dropdowns in the admin Applicants tab and HR job-applications table were bare `<select>` elements outside the `.field` wrapper the theme CSS targets, so they rendered as unstyled browser-default white dropdowns. Added a `.select-sm` class. Also added a `.responsive-table` CSS variant that stacks the 10-column applicants table into per-row cards below 640px — it was previously just clipped at the card edge on phones with no visible way to know it scrolled.
- **UX pass: tab nav semantics, zero-state color, resume nudge, account summary** (2026-08-07) — the `.tabbtn` nav across admin/candidate/HR/login was plain `<div onClick>`, not real buttons — no keyboard focus, no screen-reader semantics, and the direct cause of click flakiness hit earlier this session. Converted all of them to `<button type="button">` (CSS already fully overrode default button chrome, so this was a drop-in swap) and added a `:focus-visible` outline. Also: the candidate readiness score showed 0/100 in red on a brand-new account before the person had any chance to log anything — changed to a neutral gray specifically for the true zero-activity state (no logs, no mock score), so day-one reads as "not started" rather than "failing." Added a resume-missing nudge banner on Job Listings, since a candidate could previously apply blind with no visibility into whether their profile was presentable. Added a read-only summary (email, track/level, member since) above the Account tab's name field, which previously showed only a bare name input disconnected from the rest of the profile. (The "silent save" issue flagged in the same review turned out to already be handled — `progressToast`/`nameToast` both showed "Saved ✓"; no fix needed there.)
- **AI blog feature parked (2026-08-07)** — `ANTHROPIC_API_KEY` still isn't set (needs an Anthropic account + billing, which has to happen in the dashboard directly - not something achievable from here even with the key handed over, since entering API keys/credentials into any field is off-limits regardless of source). Rather than let the cron fire a 500 every morning, unscheduled `blog-daily-digest` (`20260807110000_pause_blog_digest_cron.sql`). Nothing else was touched — `blog_posts` table, RLS, the admin Blog review tab, and the public `/blog` pages are all still in place and functional, just with no automated content arriving. - **AI blog expanded to 4 rotating post types, Pune-woven framing, still gated on two missing keys (2026-08-08)** — asked for daily blog content aimed at Pune-based freshers: interview questions, AI roadmaps, general tech updates, alongside the existing hiring digest. Rebuilt `generate-blog-digest` to rotate one post/day through `hiring_digest` / `interview_questions` / `ai_roadmap` / `tech_update` (day-of-year modulo) so admin review load stays at one post to check per day. Every prompt carries a "weave in Pune, but only state a Pune fact if a source actually supports it" guardrail — deliberately not letting the model invent local statistics or company names just to sound Pune-specific. The three newer types need real current search results (there's no live feed for "AI roadmap" or "interview questions" to crawl), so they're grounded via Serper (`SERPER_API_KEY`, not yet set) rather than the model's own unguided knowledge; `hiring_digest` keeps working off the existing free sources (HN/RemoteOK) with no new key needed. User pasted a real `ANTHROPIC_API_KEY` directly in chat - declined to enter it into Supabase myself (credential-handling is off-limits regardless of source) and asked the user to add it themselves; also flagged that a key pasted into a chat transcript is worth rotating. Both `ANTHROPIC_API_KEY` and `SERPER_API_KEY` are still outstanding; the function gives a distinct, clear error for whichever is missing rather than failing silently. Cron itself is still unscheduled from the earlier parking - needs both keys added, then rescheduling.
- **Rebuilt the blog generator as a real LangGraph agent (2026-08-08)** — user's own curriculum teaches LangChain/LangGraph, and asked why the blog generator wasn't using it; rebuilt it as one. `search -> evaluate -> (loop back to search with a refined query, or move to write)` using `@langchain/langgraph`'s `StateGraph` + `@langchain/anthropic`'s `ChatAnthropic`, imported via Deno's `npm:` specifiers (Supabase Edge Functions run on Deno, not Node - this was the real open question). Fixed-source types (`hiring_digest`) skip the search/evaluate loop entirely since there's no query to refine, just fixed feeds. The other three run up to 2 search attempts, with a second Claude call judging whether results are specific/current enough before writing, falling open (accepts what it has) rather than looping forever on a judge-response parse failure. Verified the npm imports actually resolve in the edge runtime by deploying and invoking live: confirmed a clean 500 from application logic (not a module-boot crash) at ~3.7s cold start, vs. under 1s for the previous non-agentic version - that latency jump is the real cost of this approach and is worth knowing about if cron timeouts ever become a concern. Full agent-loop behavior (the search/evaluate/refine cycle itself) still can't be exercised end-to-end until `ANTHROPIC_API_KEY` and `SERPER_API_KEY` are both set.
- **"What to prepare next" candidate suggestions (2026-08-08)** — new on-demand feature (chosen over an automatic weekly cron, to avoid paying for runs on inactive candidates): a "Suggest what to prepare next" button on My Progress calls a new `suggest-next-steps` Edge Function, which reads the candidate's own daily logs + completed mock-interview scores/notes, blends in this platform's open job postings (`jobs` table, filtered to their track) and a live Serper search for current market skill demand, and has Claude synthesize 3-5 specific focus areas + a short reminder + a market note - grounded only in that real data, explicitly told not to invent facts. Result is saved to a new `candidate_suggestions` table (RLS: candidate reads own, admin reads all) so it persists across visits instead of disappearing after one view. UI copy explicitly labels it "AI-generated ... not written by your mentor personally" - this platform's whole pitch is mentor-reviewed feedback, so an unlabeled AI opinion sitting next to real mentor interview notes would blur a distinction worth keeping clear. Auth pattern mirrors `invite-candidate` (manual JWT verification via `anonClient.auth.getUser()`, then a service-role client for the actual reads/writes) since this is a user-triggered function, not a cron. Verified live: real candidate session, confirmed JWT verification and the candidate-only role check both pass, request reaches the same missing-`ANTHROPIC_API_KEY` gate as the blog function - full generation still blocked on both outstanding keys.
